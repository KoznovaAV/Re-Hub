# Re:Hub — Контур MVP

Сервис для контроля передачи оригиналов документов клиентами КЦР. Администратор загружает справочник и срезы, отбирает клиентов для обзвона. Операторы самостоятельно берут и передают клиентов, фиксируют звонки и договорённости.

## Возможности

- Импорт XLSX с предпросмотром, проверкой строк и выгрузкой ошибок в CSV. Корректные строки можно принять отдельно после подтверждения.
- Выбор периода и отображение даты среза. Фильтры по количеству документов, доле задолженности, типу клиента и истории звонков.
- Рабочее место оператора: свои клиенты, свободный пул, передача коллеге и освобождение клиента.
- Карточка с контактами, последним звонком, количеством недозвонов, датой обратного звонка и обещанным сроком передачи документов.
- История срезов, динамика внутри периода, регистрация претензий и санкций с реквизитами официального письма.
- Стенд `/study` для регистрации времени выполнения заданий и выгрузки протокола JSON/CSV.

Основные экраны работают через Go API и PostgreSQL. Назначения, звонки и результаты импорта сохраняются после перезагрузки. Переключение ролей остаётся демонстрационным; промышленная аутентификация не реализована.

## Проверка гипотезы H-00

Предположение: Re:Hub сокращает время подготовки корректного списка обзвона минимум вдвое относительно Excel.

**Предварительный пользовательский замер:** один участник подготовил правильный список на наборе B за **36,076 с в Excel** и **7,329 с в Re:Hub**. В этом сравнении Re:Hub быстрее в **4,92 раза**, время сократилось на **79,7%**. В обоих ответах precision и recall — 100%.

Excel измерен внешним секундомером со слов участника, Re:Hub — таймером стенда. Все попытки выполнил один человек; повторный проход под кодом P02 не считается вторым участником. Из-за повторений и разных границ замера результат остаётся предварительным: пилот с двумя администраторами ещё не завершён. [Результаты, исходные наблюдения и ограничения](reports/h00/single-participant.md).

Корректность отбора проверена программно на 30 и 4000 синтетических клиентах: списки полностью совпали с контрольными, precision и recall равны 1, ошибочных включений исключённых нет. [Результаты технического эксперимента](reports/h00/automated.md).

Для замеров людьми откройте `/study`: два участника выполняют четыре задания в перекрёстном порядке Excel/Calc и Re:Hub. Таймер фиксирует время от предъявления задания до сохранения ответа. [Инструкция](docs/scenarios/user-measurements.md). Работа таймера и экспорта проверена [автоматизированным браузерным сценарием](reports/h00/browser-workflow-method.md); его интервалы не используются как времена людей.

## Качество исходных данных: P-04

В срезе 4205 уникальных ID; 243 отсутствуют в справочнике — **5,78%**, что выше порога H-10 в 5%.

Исходный XLSX и два независимых PDF-движка дают одинаковое множество из 5873 ID справочника. Poppler пропускает 1732 ID и даёт альтернативные 1527 неизвестных клиентов. Число 1572 не воспроизведено и исключено из выводов. Технический аудит P-04 завершён; деловую причину отсутствия 243 клиентов должен уточнить поставщик. [Расчёт, хеши и версии](reports/p-tasks/data-quality.md).

## Запуск

Нужны Git и Docker с Compose v2.

```bash
git clone https://github.com/KoznovaAV/Re-Hub.git
cd Re-Hub
docker compose up --build -d --wait
docker compose ps
```

Открыть [рабочий интерфейс](http://127.0.0.1:3000/), [стенд замеров](http://127.0.0.1:3000/study) или [свободную демонстрацию](http://127.0.0.1:3000/pilot).

В GitHub Codespaces откройте порт 3000 через вкладку Ports. Если порт занят, задайте `WEB_PORT=3001` в локальном `.env` и повторите запуск. PostgreSQL хранит данные в отдельном томе; миграции применяются при старте Go.

Обновление:

```bash
git switch main
git pull --ff-only origin main
docker compose up --build -d --wait --remove-orphans
```

Остановка: `docker compose down`. Логи: `docker compose logs --tail=80`. Пароль БД по умолчанию предназначен для локального запуска; [настройка сервера](deploy/README.md).

## Проверки

```bash
make smoke
docker compose exec -T parser-service python - < scripts/smoke-parser.py
python3 -m pip install -r parser-service/requirements-import.txt
(cd parser-service && python3 -m unittest discover -s tests -v)
python3 -m unittest discover -s scripts/tests -v
(cd frontend && npm ci && node --test src/*.test.mjs)
```

Go-тесты выполняются из `backend`: `go test -p 1 ./...`. Интеграционным тестам нужна отдельная PostgreSQL в `TEST_DATABASE_URL`.

В PowerShell smoke запускается так:

```powershell
Get-Content -Raw scripts/smoke.mjs | docker compose exec -T frontend node --input-type=module -
```

CI проверяет Python, Go/PostgreSQL, интерфейс, Compose, безопасность и сборку трёх Docker-образов. [Проверки задач P-01–P-08](reports/p-tasks/README.md), [нагрузка парсера с p95 и RSS](reports/p-tasks/performance.md).

## Структура

| Каталог | Назначение |
|---|---|
| `frontend` | Интерфейс, прокси к Go и стенд замеров |
| `backend` | Go API, доменные правила и запись в PostgreSQL |
| `parser-service` | Парсинг XLSX и проверка JSON-контракта |
| `contracts` | Общий контракт и тестовые данные |
| `reports` | Расчёты, результаты проверок и ограничения |
| `deploy` | Настройка публикации и отката |

Python проверяет структуру книги и ячейки; Go проверяет дубли, клиента, период и числовые ограничения. Отсутствующее «Всего» наследуется только из более раннего среза той же пары клиент/период; значение и источник сохраняются. Отсутствие клиента в срезе не считается нулевым долгом.
