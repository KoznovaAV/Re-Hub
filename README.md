# Re:Hub — Контур MVP

Re:Hub помогает администратору и оператору КЦР контролировать передачу оригиналов документов. Целевой сценарий: администратор загружает срез, сравнивает динамику по периодам и формирует список на обзвон. Оператор фиксирует результат звонка и видит историю клиента.

## Что доступно в прототипе

| Функция | Состояние | Как посмотреть |
|---|---|---|
| Интерфейс, Go API и Python | Реализованы точки входа и `/health` | Запуск через Compose, затем проверка ниже |
| Обмен Go ↔ Python | Контрольный JSON-запрос с фиксированным идентификатором | `make smoke` |

| CI/CD | Проверки PR, сборка образов, деплой и откат через SSH | [Настройка CI/CD](deploy/README.md) |

## Сценарий после ревью

Администратор выбирает период на главной, открывает клиентов, задаёт количество документов, долю долга и историю звонков. Включает кандидатов на обзвон, проверяет счётчик, выгружает CSV или добавляет выбранных в пул. Оператор начинает с "Мои клиенты"; свободный пул и общий список нужны для распределения и передачи. В карточке сверху контакт и последнее общение. Перенос звонка требует отдельной даты. Администратор готовит список и не назначает операторов. Операторы берут клиентов, забирают чужих себе, передают своего клиента коллеге и освобождают вручную. Назначение сохраняется в базе с аудитом. Отказ фиксируется в истории без автоматического закрытия клиента.

[Требования ревью и ограничения](docs/scenarios/customer-review.md). [Роли и статусы](docs/scenarios/roles-and-statuses.md). [Статус H-00 и критерии пилота](reports/H-00-status.md): подтверждение требует пользовательских замеров.

## Как это работает

Браузер запрашивает `/api/probe` у сервера интерфейса, который передаёт запрос в Go. Go отправляет в Python `POST /probe` с JSON `{"schema_version":1,"request_id":"skeleton"}` и проверяет, что Python вернул ту же версию и идентификатор со статусом `ok`. При недоступности Python маршрут проверки возвращает 503, а `/health` Go остаётся доступным.

## Архитектура и структура

Целевой паттерн — модульный монолит Go для доменных правил и записи в PostgreSQL. Python выделен для парсинга XLSX и взаимодействует с Go по JSON/HTTP. На этапе скелета используется один контрольный запрос. Контрольный запрос сохраняется для проверки границы компонентов. Go API дополнен PostgreSQL и импортом XLSX через Python.

## Как запустить через Docker

Для локальной работы нужны Git и запущенный Docker Desktop (Windows/macOS) или Docker Engine с плагином Compose v2 (Linux). Проверить, что Docker запущен и Compose доступен, можно командами `docker info` и `docker compose version`. Для запуска нужны Compose v2 с поддержкой `up --wait` и доступ к реестру образов при первой сборке.

### Первый запуск

```bash
git clone --branch main https://github.com/KoznovaAV/Re-Hub.git
cd Re-Hub
docker compose up --build -d --wait
docker compose ps
```

Compose собирает фронтенд, Go API и Python-сервис, запускает PostgreSQL и применяет миграции при старте Go. Откройте [главную](http://127.0.0.1:3000/). В обычном режиме доступны главная, клиенты, карточки, рабочая очередь, история и экран импорта. Экраны работают с PostgreSQL через Go API. Импорт отправляет настоящий XLSX парсеру: сначала предпросмотр, затем подтверждение. При ошибках требуется явное согласие на приём только корректных строк. PostgreSQL поднимается автоматически в Compose и хранит данные в отдельном томе. Файлы заказчика базовому запуску не нужны. Основные экраны читают и сохраняют данные через Go API. Данные сохраняются после перезагрузки страницы. Пароль БД по умолчанию предназначен для локального демо; для сервера используйте [отдельную конфигурацию](deploy/README.md).

### GitHub Codespaces

В терминале Codespace из корня репозитория:

```bash
git pull --ff-only
WEB_PORT=3000 docker compose up --build -d --wait --remove-orphans
docker compose ps
```

Во вкладке Ports добавьте 3000, если он не появился, затем Open in Browser. Дополнительные Compose-файлы не нужны. При обновлении `--remove-orphans` убирает старый контейнер переименованного сервиса; том PostgreSQL сохраняется.

### Проверка запуска

PowerShell:

```powershell
Get-Content -Raw scripts/smoke.mjs | docker compose exec -T frontend node --input-type=module -
```

Bash:

```bash
docker compose exec -T frontend node --input-type=module - < scripts/smoke.mjs
```

Ожидаемый результат - 10 из 10 успешных JSON-запросов через Go и Python. При установленном Make можно использовать `make up`, `make smoke` и `make down`.

### Обновление и остановка

В рабочей копии с чистой веткой `main`:

```bash
git switch main
git pull --ff-only origin main
docker compose up --build -d --wait
```

Чтобы остановить контейнеры, выполните `docker compose down`. Если сервис не запустился, посмотрите `docker compose ps -a` и `docker compose logs --tail=80`. Если порт 3000 занят, добавьте `WEB_PORT=3001` в локальный `.env` в корне репозитория, повторите запуск и откройте [порт 3001](http://127.0.0.1:3001/).

### Проверка отказа и восстановления

```bash
docker compose stop parser-service
docker compose exec -T -e SMOKE_PYTHON_DOWN=1 frontend node --input-type=module - < scripts/smoke.mjs
docker compose up -d --wait parser-service
make smoke
```

При остановке Python ожидаются ответ Go `/health` с кодом 200 и `/api/probe` с кодом 503. После запуска Python smoke снова ожидает 10 успешных ответов.

### Запуск без Docker

В трёх терминалах из корня репозитория:

```bash
python3 parser-service/app/main.py
(cd backend && go run ./cmd/api)
node frontend/src/server.mjs
```

После запуска: `node scripts/smoke.mjs`. Остановите процессы через Ctrl+C. Для Compose используйте `docker compose down`. Логи сервисов доступны через `docker compose logs --tail=50`.

## Настройки, данные и доступы

## Работа с данными после ревью заказчика

Администратор загружает клиентов, затем срез с выбранной датой. Используется согласованный формат «Все КЦР» для справочника и профиль вкладок для срезов. Файл проверяется до записи, ошибки доступны в CSV. Срезы разных дат сохраняются отдельно. Отсутствие клиента в новом срезе не считается нулевым долгом. «Всего» наследуется только внутри того же отчётного периода.

Администратор отбирает клиентов по периоду, количеству, доле, типу и истории звонков и добавляет их в пул. Обычный клиент с долей менее 5% не добавляется. Для новичка используется явный тег «Новичок» или дата подключения в модели данных. Операторы видят подготовленный пул и назначенных клиентов. В карточке своего клиента доступны «Передать оператору» и «Освободить». Администратор не распределяет клиентов между операторами.

После контакта оператор может указать фактическую дату события в прошлом, комментарий, обещанный срок из списка или свою дату. Перенос звонка хранится отдельно от срока передачи документов. Администратор регистрирует номер, дату официального письма и статус претензии/санкции. Перезагрузка страницы сохраняет эти данные.

Переключение пользователей остаётся способом демонстрации ролей с тестовыми идентификаторами. Это не промышленная аутентификация. Для отдельного просмотра синтетического интерфейса без базы запустите `REHUB_MODE=demo node frontend/src/server.mjs`. В Compose по умолчанию включена работа с базой, без подмены недоступного API демо-данными.
