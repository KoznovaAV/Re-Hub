# H-02. План проверки маршрутизации

Вопрос: даёт ли сторонний маршрутизатор заметное улучшение для текущего сценария Re:Hub? Контроль — стандартный `http.ServeMux`. Варианты — chi v5.2.3 и Gin v1.11.0. Все регистрируют один и тот же метод и путь. Остальной код, запросы, Python и настройки не меняются.

Проверяются два режима:

1. `route`: маршрутизатор отдаёт фиксированный JSON. Этот режим показывает накладные расходы маршрутизации вместе с локальным HTTP.
2. `probe`: тот же маршрутизатор вызывает обработчик из Go API. Обработчик отправляет контрольный JSON действующему Python-сервису. Этот режим определяет решение для скелета.

Один клиент, один запрос одновременно, HTTP/1.1 и повторное использование соединения с Go. Для каждого режима пять раундов с ротацией порядка вариантов. Каждый вариант запускается отдельным процессом. После 250 запросов прогрева выполняются 2 000 измеряемых запросов. Нагрузка, прогрев и число повторов одинаковы для всех вариантов. На каждой операции проверяются HTTP 200 и точное содержимое JSON.

Записываются число ошибок, p50, p95, запросы в секунду и пиковый RSS процесса на Linux. Задержки считаются по полному запросу клиента. Итог — медиана пяти раундов для каждой метрики. RSS показывает память бинарника эксперимента со всеми тремя роутерами, поэтому его нельзя переносить на отдельную сборку продукта. Сложность поддержки оценивается по числу прямых зависимостей и необходимой обвязке одного маршрута.

Решение до прогона: оставить `net/http`, если он проходит проверку корректности. Перейти на сторонний роутер для текущего сценария, только если у него ноль ошибок в обоих режимах, медианный p95 в режиме `probe` ниже минимум на 15%, медианная пропускная способность выше минимум на 10% и p95 ниже контроля минимум в четырёх из пяти раундов. Изолированное ускорение `route` само по себе не меняет решение.

Эксперимент не измеряет нагрузку с параллельными операторами, базой или ML. Человеко-часы фиксируются отдельно по журналу участников. Время выполнения команд не заменяет этот журнал.
