# Как продемонстрировать проверку H-00

## Что говорить в начале

«Проверяем, помогает ли единый интерфейс формировать список обзвона быстрее ручной работы без ухудшения качества. Технический эксперимент уже выполнен на 30 и 4000 клиентах. Сейчас покажем метод пользовательской проверки на учебном наборе. Пример времени смоделирован: реальных участников в нём нет».

Не называть виртуальных участников сотрудниками заказчика. Не представлять смоделированные секунды как замер. Оценка 15–20 часов из брифа относится к полному рабочему процессу, а не к этим 15 клиентам.

## Подготовка

В рабочей копии репозитория переключиться на опубликованную ветку:

```bash
git fetch origin
git switch fix/review-roles-and-workflow
git pull --ff-only
docker compose up --build -d --wait --remove-orphans
```

Открыть `http://127.0.0.1:3000/pilot`. В Codespaces открыть порт 3000 через Ports, затем добавить `/pilot` к адресу. Страница содержит два синтетических набора по 15 клиентов и работает независимо от содержимого PostgreSQL. Это отдельный упрощённый стенд фильтрации, а не весь основной интерфейс.

Нужны браузер и Excel либо LibreOffice Calc. Открыть рядом [результат технического эксперимента](../../reports/h00/automated.md) и [смоделированный учебный расчёт](../../reports/h00/simulated-pilot.md).

## Показ за 5–7 минут

1. **Задание, 30 секунд.** Выбрать III квартал 2026. Нужно включить клиентов, у которых есть наблюдение, не передано не менее восьми документов, нет исключения и не было звонка по этому кварталу. Зафиксировать правила до отбора. Неполное наблюдение не считать нулевым долгом.
2. **Исходная таблица, 1–2 минуты.** Выбрать набор A и скачать исходные строки CSV. Открыть файл в Excel/Calc: разделитель — запятая. Показать фильтрацию `period=2026Q3`, `unsent>=8`, `contacted=0`, `excluded=0`, непустое `unsent`. Записать итоговые ID в отдельный список. Это демонстрация ручного пути; время выступления не считать результатом реального пилота.
3. **Интерфейс, 1 минута.** На `/pilot` установить A, `2026Q3`, порог 8. Список: `PILOT-04`, `PILOT-05`, `PILOT-12`. Нажать «Скачать список обзвона CSV». В карточке `PILOT-01` показать различие отсутствия наблюдения и числового нуля. Переключить набор на B: список `PILOT-19`, `PILOT-20`, `PILOT-27`.
4. **Учебный расчёт, 1 минута.** Показать таблицу из simulated-pilot.md. Две придуманные Excel-длительности: 110 и 90 секунд. Две придуманные длительности Re:Hub: 42 и 35 секунд. Медианы: 100 и 38,5 секунды, отношение 2,60. В примере Re:Hub выдаёт все три правильных ID в каждом наборе. Цифры объясняют расчёт, но не доказывают реальное ускорение.
5. **Контрпример, 30 секунд.** В смоделированном ошибочном варианте в список Re:Hub добавлен исключённый клиент. Скорость та же, но критерий качества не выполнен. Показать `criteria_met=false`: быстрый неправильный список не подтверждает гипотезу.
6. **Вывод, 30 секунд.** «Корректность программного отбора проверена самостоятельно. Для проверки скорости людей подготовлены одинаковое задание, контрольные данные и способ расчёта. Пользовательский эффект пока не измерен».

Один учебный набор содержит только три подходящих клиента. Его достаточно, чтобы объяснить методику, но мало для убедительного вывода о качестве на рабочих данных. Наборы A и B имеют одинаковый рисунок случаев и разные ID. Для настоящего пилота нужны сопоставимые по сложности, но разные истории, чтобы повторение не подсказывало ответ.

## Как показать расчёт командой

Из корня репозитория:

```bash
python3 scripts/evaluate-h00.py contracts/testing/h00/simulated/pilot.json
python3 scripts/evaluate-h00.py contracts/testing/h00/simulated/pilot-failed-quality.json
```

В PowerShell вместо `python3` использовать `py -3`. В первом выводе `data_kind=simulated`, `human_participants=0`, `criteria_met=true`, **`confirmed=false`**. Во втором критерий качества не выполнен, итог также `confirmed=false`.

## Как получить настоящий результат

Два реальных администратора выполняют по два задания без подсказок:

| Порядок | Участник 1 | Участник 2 |
|---|---|---|
| Первый проход | Excel, набор A | Re:Hub, набор A |
| Второй проход | Re:Hub, набор B | Excel, набор B |

До этого эксперт проверяет эталон. Для более надёжного пилота подготовить различные сопоставимые наборы и перемешать порядок строк. Оба инструмента должны получать одинаковые данные и одно задание. Зафиксировать заранее, включается ли открытие файла в время, и применить одинаковое правило.

Старт — выдача задания и доступа к данным. Финиш — сохранение окончательного списка ID. Записать реальные секунды и ID каждого прохода, не округляя до желаемого порога. Если потребовалась подсказка, сохранить это в протоколе и не считать проход самостоятельным.

Использовать отдельный журнал с `data_kind=measured`, настоящими обезличенными кодами участников и согласованным эталоном. Не переименовывать simulated/pilot.json в реальный журнал. Рассчитать отношение медиан, precision, recall и число ошибочно включённых исключённых. Критерии: отношение >=2, precision >=0,8, recall >=0,9 и 0 включений исключённых в каждом проходе Re:Hub. При двух участниках вывод относится к этому небольшому пилоту, а не ко всем сотрудникам.

Демонстрация сохранности рабочего продукта проводится отдельно на главном экране: администратор готовит пул, оператор берёт клиента, фиксирует событие, передаёт его коллеге; после перезагрузки данные остаются. Это проверяет функции, но не заменяет четыре пользовательских замера.
