# Как продемонстрировать проверку H-00

## Подготовка

В рабочей копии репозитория:

```bash
git fetch origin
git switch docs/h00-simulated-pilot
git pull --ff-only
docker compose up --build -d --wait --remove-orphans
```

Открыть http://127.0.0.1:3000/pilot. В Codespaces открыть порт 3000 через Ports и добавить /pilot к адресу. Страница использует два синтетических набора по 15 клиентов и не зависит от содержимого PostgreSQL. Это отдельный упрощённый стенд фильтрации.

Подготовить браузер, Excel либо LibreOffice Calc и [учебный пример](../../reports/h00/simulated-pilot.md). Ветка docs/h00-simulated-pilot содержит только учебные материалы и дополнение /pilot. Подготовленные ранее изменения основного приложения в неё не входят.

## Вступление

«Проверяем, помогает ли единый интерфейс формировать список обзвона быстрее ручной работы без ухудшения качества. Сейчас покажем метод проверки на учебном наборе. Пример времени смоделирован: реальных участников в нём нет».

Виртуальных участников не называть сотрудниками заказчика. Придуманные секунды не называть замером. Оценка 15–20 часов из брифа относится к полному рабочему процессу, а не к этим 15 клиентам.

## Показ за 5–7 минут

1. **Задание, 30 секунд.** Выбрать III квартал 2026. Нужно включить клиентов с наблюдением, не менее восьми непереданных документов, без исключения и без звонка за этот квартал. Правила определить до отбора.
2. **Таблица, 1–2 минуты.** На /pilot выбрать A, скачать исходные строки CSV. Открыть в Excel/Calc, разделитель — запятая. Показать фильтры: period=2026Q3, unsent>=8, contacted=0, excluded=0, непустое unsent. Сохранить итоговые ID отдельно. Время выступления не считать временем реального пользователя.
3. **Интерфейс, 1 минута.** Выбрать A, 2026Q3, порог 8. Результат: PILOT-04, PILOT-05, PILOT-12. Нажать «Скачать список обзвона CSV». В карточке PILOT-01 показать отсутствие наблюдения в III квартале: это не числовой ноль. Переключить B: PILOT-19, PILOT-20, PILOT-27.
4. **Расчёт, 1 минута.** Показать вымышленную таблицу: Excel — 110 и 90 с; Re:Hub — 42 и 35 с. Медианы 100 и 38,5 с; отношение 2,60. Эти цифры объясняют расчёт, но не доказывают ускорение людей.
5. **Контрпример, 30 секунд.** Показать вариант с ошибочным включением исключённого клиента. При той же скорости criteria_met=false. Качество должно проверяться вместе со скоростью.
6. **Вывод, 30 секунд.** «Подготовлены задание, контрольные данные и способ расчёта. Пользовательский эффект ещё не измерен. Смоделированный пример не подтверждает гипотезу».

Один набор содержит только три подходящих клиента. Этого достаточно для объяснения методики, но мало для убедительного вывода о качестве на рабочей базе. У A и B одинаковый рисунок случаев и разные ID. В настоящем пилоте нужны разные сопоставимые истории, чтобы повторение не подсказывало ответ.

## Команды для расчёта

Из корня репозитория:

```bash
python3 scripts/evaluate-h00.py contracts/testing/h00/simulated/pilot.json
python3 scripts/evaluate-h00.py contracts/testing/h00/simulated/pilot-failed-quality.json
```

В PowerShell использовать py -3 вместо python3. В первом выводе data_kind=simulated, human_participants=0, criteria_met=true, **confirmed=false**. Во втором качество не проходит критерий и confirmed также false.

## Настоящий пользовательский пилот

| Порядок | Участник 1 | Участник 2 |
|---|---|---|
| Первый проход | Excel, A | Re:Hub, A |
| Второй проход | Re:Hub, B | Excel, B |

До начала эксперт проверяет эталон. Подготовить разные сопоставимые наборы и перемешать порядок строк. Для обоих инструментов задать одинаковые данные и правила. Заранее определить, входит ли открытие файла в отсчёт времени, и применить одинаковое условие.

Старт — выдача задания и доступа к данным. Финиш — сохранение окончательного списка ID. Записать реальные секунды и итоговые ID без подсказок и подгонки под порог. Подсказки фиксировать в протоколе.

Использовать новый журнал с data_kind=measured, настоящими обезличенными кодами участников и утверждённым эталоном. Не переименовывать simulated/pilot.json в реальный журнал.

Критерии: отношение медиан >=2, precision >=0,8, recall >=0,9, включений исключённых клиентов 0 в каждом проходе Re:Hub. Два участника дают результат небольшого пилота, а не доказательство для всех сотрудников.
