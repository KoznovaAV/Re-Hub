# Разбор запросов в Re:Hub

Модель переводит одну реплику сотрудника в JSON. Например, "Покажи должников за 3 квартал 2026" превращается в `list_debtors`, период `2026Q3`, минимум один непереданный оригинал. "Когда DEMO-06 обещал передать оригиналы за 3 квартал 2026?" превращается в `get_client_promise`. За датой и источником обращается Go после проверки прав.

Тестовые вопросы основаны на ТЗ заказчика, описании текущего процесса и ответах В-06 и В-17. В-17 различает обещанный срок передачи и дату следующего контакта. Для неоднозначного вопроса о сроке предусмотрено уточнение. Контракт предусматривает `unsupported_filter` для фильтров по проценту, VIP, этапу работы и истории звонков и `document_content` для запроса о содержимом письма или файла.

Разборщик возвращает `intent`, `period`, `client_ref`, `min_unsent` и `reason`. Неиспользуемые поля равны `null`. Python проверяет форму и параметры запроса. При интеграции Go должен получить пользователя из серверной сессии и проверить доступ до чтения данных. Дату и источник для ответа возвращает сервис, который прочитал запись.

Лимит одного вопроса - 2 000 символов. Допустимый порог `min_unsent` - от 1 до 1 000 000 документов. Если явно указанный период не совпадает с параметром чтения или модель не смогла привязать клиента к вопросу, разборщик возвращает уточнение. Для невалидного JSON или нарушения структуры ответа разборщик возвращает ошибку.

## Сценарии интеграции

- `SYN-01` и `SYN-02` различают нулевой долг и отсутствие наблюдения за период.
- `SYN-06` проверяет, что оператору недоступны данные чужого клиента.
- `SYN-09` проверяет обещанный срок 29.11.2026 и источник `test-call-19`.

## Проверка

Набор `contracts/eval/intent-cases-v1.jsonl` содержит 20 основных реплик, 3 уточнения, 10 запросов на отказ и 3 случая вне текущего охвата. Для H-03 ещё предстоит проверить фактические ответы и права через API и сравнить время выполнения задач с обычными фильтрами.

Из каталога `ai-service`:

```bash
python -m unittest discover -s tests
python -m app.ml_intent_eval ../contracts/eval/intent-*.jsonl --check-fixtures
```

Для прогона на модели запустите локальный Ollama и скачайте модель:

```bash
ollama pull qwen3:4b
python -m app.ml_intent_eval ../contracts/eval/intent-cases-v1.jsonl --warmup > intent-report.json
```

Скрипт выводит ожидаемый и полученный JSON по каждой реплике и сводку по категориям. Медиана исключает запросы с техническими ошибками. Флаг `--warmup` выполняет один дополнительный запрос до замера и записывает его отдельно. Код выхода 1 означает расхождение или ошибку прогона.

В `metadata` сохраняются версия Ollama, digest модели, версия справочника периодов и SHA-256 справочника и промпта. Если метаданные провайдера недоступны, причину можно посмотреть в `metadata_errors`. Для проверки на конкретной версии сервера передайте `--require-ollama-version <версия>`. Запускайте скрипт из дерева репозитория со справочником периодов и промптом.

## Синтетические данные для проверки чтения

В `contracts/eval/synthetic-client-data-v1.json` лежат 30 вымышленных клиентов, 86 наблюдений за три квартала и 10 обещанных сроков. Это фикстура для тестов чтения, в которой объединены оба режима ключей. Для импорта каждый режим проверяется отдельным файлом.

В `contracts/eval/intent-synthetic-v1.jsonl` поле `expected` задаёт ожидаемый разбор вопроса. Дополнительное поле `expected_read` задаёт результат для будущей проверки Go от имени указанного тестового оператора. В нём различаются нулевой долг, отсутствующее наблюдение, пустой список и недоступная запись. Статус `unavailable` обозначает отсутствие доступной записи в тесте и не задаёт HTTP-статус. Текущий runner проверяет только `expected`.

## Локальный сквозной запуск через Go

Дополнительный файл Compose включает `POST /ai/query` для синтетических данных. Запросы исполняются от имени фиксированного тестового оператора `test-op-a`. Поле `client_external_id` может только сузить выборку. Серверная авторизация и чтение из PostgreSQL потребуются для работы с данными заказчика.

Из корня проекта в PowerShell с Docker Desktop и запущенным Ollama:

```powershell
ollama list
docker compose -f docker-compose.yml -f docker-compose.ai-demo.yml up --build -d --wait
$body = @{ query = 'Сколько оригиналов ждём от TST00001 за 3 квартал 2026?' } | ConvertTo-Json -Compress
Invoke-RestMethod http://127.0.0.1:8080/ai/query -Method Post -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body)) | ConvertTo-Json -Depth 6
```

Для проверки четырёх сценариев из корня проекта запустите `py -3 scripts/smoke-ai-query.py`.

В ответе для `TST00001` ожидаются `status: ok`, `unsent_docs: 0` и источник `test-slice-2026-10-20`. Для `TST00002` ожидается `no_data`. Остальные сценарии перечислены в `intent-synthetic-v1.jsonl`. Если сервис возвращает 502, проверьте запуск Ollama, наличие модели `qwen3:4b` и доступность Ollama из Docker. Адрес можно задать через `OLLAMA_BASE_URL`.

```powershell
docker compose -f docker-compose.yml -f docker-compose.ai-demo.yml down
```
