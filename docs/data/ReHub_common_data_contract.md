# Re:Hub — общий контракт данных v1

**Версия обмена:** `1.0`. **Статус документа:** рабочая спецификация для ревью команды. Подтверждение поставщиком смысла исходных данных и принятие технических решений не подразумеваются.

**Назначение:** одинаковые имена полей, типы, ключи, периоды, ошибки и правила записи во всех частях Re:Hub. Этот файл — общая точка ссылки. Порядок фиксации правил и критерии задачи находятся в [T-02_import_and_period_rules.md](T-02_import_and_period_rules.md).

**Роли:** Александр — Go; Артём — Python backend; Варвара пишет парсер в помощь Артёму; Алина — ML и семантика данных. Екатерина проверяет ожидания, Вячеслав — UI, Алексей — сценарии, Дарья — доску и организацию.

**Граница записи:** далее Go указан как предлагаемый владелец доменной валидации и commit. Александр и Артём фиксируют этот выбор в одном решении. Если выбран Python, правила целиком выполняет один доменный компонент там. Парсер Варвары в любом варианте остаётся без БД, расчётов истории и commit. Обмен — JSON; обязательный Python web framework не задаётся.

Все JSON-примеры ниже синтетические. Они описывают ожидаемую форму данных и не подтверждают запуск кода, миграций или проверку гипотез. Даты в примерах — значения данных, а не план работ.


## 1. Что фиксируем

Контракт — версия правил, по которым команда одинаково понимает поля, ошибки и результат обработки. Его принимают в репозитории: описание, JSON Schema, примеры и миграции проходят совместное ревью. Это не юридический договор.

| Контракт | Стороны | Содержание |
|---|---|---|
| C1 — исходный файл | Команда / поставщик данных | Листы, колонки, внешний ключ, период, дата наблюдения, пустые значения |
| C2 — результат парсера | Python / Go | Типизированные строки JSON, координаты, ошибки и версия |
| C3 — импорт | Go / интерфейс | Preview, подтверждение частичного импорта, commit, отчёт и повтор загрузки |
| C4 — чтение для ИИ | Go / ML-Python | Только разрешённые выборки, права пользователя, источники и применённые критерии |

C1–C3 нужны для текущего импорта. C4 не блокирует начало парсера: перечень tools и семантика фильтров согласуются отдельно. JSON — формат обмена, контракт не выбирает веб-фреймворк Python.

## 2. Ключи и типы

- `external_id`: внешний идентификатор. В тестовом режиме `anonymous` — три латинские заглавные буквы и пять цифр. В режиме `kcr` — ровно семь цифр. Режим задаётся для загрузки явно.
- `client_id`: внутренний UUID в БД/API. В исходном файле и результате парсера его нет.
- `period_code`: стабильный код периода из справочника, например `2026Q1`.
- `snapshot_date`: дата наблюдения в форме `YYYY-MM-DD`. Не время загрузки.
- Число документов: целое неотрицательное, максимум 2 147 483 647 в v1.
- Пропущенные данные не превращаются в ноль. JSON содержит настоящие числа/boolean/null, а не их строковое отображение.

Предложение v1: если ключ уже записан в Excel числом, парсер выдаёт `KEY_MUST_BE_TEXT`. Он не восстанавливает потерянные ведущие нули догадкой. Это строже старого входа, но позволяет сохранить идентичность клиента.

## 3. Формат XLSX

Базовый профиль: один XLSX, одна непустая таблица на согласованном листе, первая строка — уникальные заголовки, далее записи. Для одного вызова читается только указанный `file_kind` лист. Другие непустые листы не импортируются автоматически, в отчёте указывается, что они не обрабатывались. Объединённые ячейки в рабочей таблице, повторяющиеся заголовки и повторные названия колонок дают ошибку структуры. Полностью пустые строки пропускаются.

### Лист `clients`

| Поле | Тип | Обязательно | Обработка пустого значения |
|---|---|---|---|
| external_id | текст | Да | Ошибка строки |
| name | текст | Нет для тестовых данных | Не затирать существующее |
| inn | текст из 10/12 цифр | Нет в тестовых данных | Не затирать существующее |
| kpp | текст из 9 цифр | Нет | Не затирать существующее |
| joined_on | дата | Нет | Не затирать существующее |
| active | boolean | Нет | Не менять; для нового клиента default true |
| blocked | boolean | Нет | Не менять; новый default false |
| excluded | boolean | Нет | Не менять; новый default false |
| excluded_reason | текст | Нет | Не затирать существующее |
| tags | текст, разделитель `;` | Нет | Пустая ячейка — поле отсутствует, не менять |
| ekb_offset_hours | целое −12…14 | Нет | Не менять |
| source_status_raw | текст | Нет | Сохранить как исходный текст, без автоматической смены этапа |

Уникален `external_id`. ИНН не уникален. При повторном импорте найденный клиент обновляется только по явно переданным непустым полям. Отсутствие клиента в файле не удаляет и не отключает его. Поле null и отсутствие необязательного поля означают «не обновлять»; очищать сведения следует отдельным явным действием администратора.

`tags` после разбора — массив кодов. Начальное предложение: `vip`, `integrator`, `tech_partner`, `mpp`, `newcomer`. Отображаемые подписи и дополнительные теги согласует Екатерина. Неизвестный тег — ошибка строки; не превращать его в новый справочник автоматически. При переданном массиве Go заменяет набор тегов целиком; пустой массив допускается только при явном обозначении `[]` в источнике. Пустая ячейка не равна `[]`.

### Лист `snapshot`

| Поле | Тип | Обязательно | Значение |
|---|---|---|---|
| external_id | текст | Да | Ссылка на заранее загруженного клиента |
| period_code | текст | Да | Код из принятого справочника |
| total_docs | целое / пусто | Только для первого наблюдения пары | При пустом значении Python возвращает null |
| unsent_docs | целое | Да | Количество непереданных документов |

Дата среза задаётся один раз в контексте загрузки. Если исходный файл содержит `snapshot_date`, все непустые значения должны быть одной датой и совпадать с контекстом; иначе `SNAPSHOT_DATE_CONFLICT`. Метаданные не должны молча переопределять дату файла.

Контекст также содержит `period_scope` — список периодов в файле, и `coverage` — `unknown` или `full_declared`. Для каждого значения `full_declared` сохраняется, что это декларация поставщика, а не результат проверки полноты. Все period_code строк должны входить в scope. В v1 одна подтверждённая загрузка создаёт один срез даты, который может включать несколько периодов. Объединять разные файлы одной даты неявно нельзя.

В процентах нет входной колонки. Go вычисляет долю по принятым числам. Исторические широкие таблицы и PDF не являются базовым профилем XLSX: для них нужен отдельный адаптер с известным mapping, а не эвристика общего парсера.

## 4. Явный mapping старых названий

Предлагаемое соответствие для профиля v1:

| Старое поле | Каноническое |
|---|---|
| client_id из прежней спецификации | external_id |
| Период | period_code через явную таблицу соответствий |
| Всего документов | total_docs |
| Не передано документов | unsent_docs |

Текст «Код КЦР» и обезличенный ID — разные исходные колонки. В режиме anonymous используется обезличенный ID; в kcr — код КЦР. Если оба заполнены и противоречат выбранному режиму, ошибка, а не выбор первого непустого.

Mapping должен иметь ID и версию, например `canonical_xlsx_v1` или `customer_long_v1`. Сопоставление заголовков без учёта регистра допустимо только если оно не создаёт неоднозначность. Поиск похожих слов и выбор period по порядку строк запрещены.

## 5. Периоды

В `contracts/periods.v1.json` зафиксированы исходные окна. Границы включительные:

| Код | Подпись | Начало | Конец |
|---|---|---|---|
| Y2025 | Весь 2025 | 2025-01-01 | 2025-12-31 |
| 2025Q2_2025Q4 | 2–4 кв. 2025 | 2025-04-01 | 2025-12-31 |
| 2026Q1 | 1 кв. 2026 | 2026-01-01 | 2026-03-31 |
| 2026Q2 | 2 кв. 2026 | 2026-04-01 | 2026-06-30 |
| 2026Q3 | 3 кв. 2026 | 2026-07-01 | 2026-09-30 |
| 2025Q2_2026Q1 | 2 кв. 2025 — 1 кв. 2026 | 2025-04-01 | 2026-03-31 |

Для октябрьского XLSX H-01 подтверждена по четырём явно названным вкладкам. В PDF периоды строк отсутствуют; для текущего импорта используется [профиль XLSX](customer-october-xlsx.md).

Правила:

1. Период относится к документам, snapshot_date — к моменту наблюдения, imported_at — к загрузке. Это разные сущности.
2. Сравнение выполняется по одному `client_id + period_id` между активными версиями срезов, упорядоченными по snapshot_date.
3. Пересекающиеся окна не суммируются: «весь 2025» и «2–4 кв. 2025» содержат общие документы.
4. Новый период не равен повторному долгу. Новый цикл и хронический долг требуют отдельного согласованного правила.
5. Пустой period — `PERIOD_REQUIRED`. Незнакомый code — `PERIOD_UNKNOWN`. Справочник создаёт администратор, парсер его не расширяет.
6. По файлу без period нельзя молча назначить всем строкам текущий квартал. Допустимый отдельный режим «весь файл относится к одному периоду» добавляется только отдельным решением и проверкой — в v1 его нет.
7. Пропуск клиента/периода в срезе не равен нулю, закрытию долга или удалению. Показывается последнее наблюдение с признаком свежести; автоматическое решение об обзвоне при устаревших данных не принимается скрыто.
8. Закрытие одного квартала не закрывает другие обязательства клиента. Обещания и этапы контролируются по периодам; назначение оператора на клиента хранится отдельно.

## 6. Нормализация Python

- У текстовых полей убрать пробелы по краям, сохранить регистр и ведущие нули ключа. Никаких автоматических замен латиницы/кириллицы.
- Строковое `1 245`, неразрывный и узкий неразрывный пробел тысяч превращаются в 1245. `1 24`, `12,5`, отрицательные значения и boolean в числовой колонке отклоняются.
- Числовое значение Excel 1245.0 допускается как 1245, если оно конечное и целое; 12.5 — ошибка. Идентификаторы из числовых ячеек всё равно отклоняются.
- Пустой total_docs → null; пустой unsent_docs → ошибка. #N/A и другие ошибки Excel не превращаются в ноль.
- Даты: нативная дата Excel или `YYYY-MM-DD`; `DD.MM.YYYY` допускается в отдельном mapping. Дату без года не достраивать.
- Формулы в обязательных колонках v1 отклоняются с `FORMULA_NOT_ALLOWED`. Парсер не выполняет вычисления Excel. Для первого прохода поставщик экспортирует значения.
- Boolean базового профиля — true/false, 1/0, да/нет. Специфические «Дейсвующий»/«Не действующий» поддерживаются только в согласованном mapping.
- Пустые значения optional полей clients опускаются. Дубли строк не удаляются. Номер строки — реальный номер строки Excel, начиная с 1.

## 7. Ответ парсера

См. `contracts/parser-result.schema.json` и примеры. У каждой нормализованной строки есть `source.sheet`, `source.row` и `data`. Ошибка включает scope, code, message, источник и raw_value. Для каждой непустой исходной строки возвращается либо нормализованная строка, либо одна или несколько row-ошибок. Одна исходная строка не может одновременно оказаться в обоих списках.

Структурные ошибки файла возвращаются отдельно: даже если какие-то строки удалось разобрать, Go не подтверждает такой импорт. Пустой лист с одними заголовками также отклоняется. Неожиданный сбой процесса не маскируется пустым «успешным» JSON.

## 8. Семантическая проверка единого доменного компонента

Порядок проверки:

1. Проверить JSON-версию и схему.
2. При file-ошибках завершить preview как rejected.
3. Проверить дубли на всех сохранившихся ключах источника, включая строки с другими ошибками: `(external_id)` для clients, `(external_id, period_code)` для snapshot. Точный повтор тоже ошибка файла.
4. Проверить period_scope и существование period_code.
5. Проверить существование external_id для среза; клиента из среза не создавать.
6. Для каждой допустимой пары разрешить total_docs.
7. Проверить `0 ≤ unsent_docs ≤ total_docs`, обязательность total и отсутствие противоречий.
8. Сформировать preview, список отклонённых строк и признак неполноты.

Чтобы пункт 3 работал, row-ошибки парсера должны содержать `key_hint` с external_id и period_code, если их удалось прочитать. Go учитывает эти ключи для поиска дублей. Если ключ неизвестен из-за ошибки самой ячейки, дублирование этой пары нельзя достоверно проверить; такая строка остаётся отклонённой, это ограничение отражается в отчёте.

### Пропущенный total_docs

Go ищет последнее принятое значение **той же пары** client + period среди активных версий срезов с датой строго раньше новой snapshot_date. В БД сохраняются принятый total_docs и ссылка на источник наследования.

Если источника нет — `TOTAL_MISSING_FIRST_OBSERVATION`. Если unsent выше найденного total — `UNSENT_GT_TOTAL`. При total=0 и unsent=0 процент не определён (`null`), а не 0%.

Предложение v1 для исторических загрузок: если дата раньше уже имеющегося наблюдения этой пары, все total_docs должны быть заданы явно. Поздний исторический импорт не меняет ранее сохранённые значения и источники наследования будущих срезов. Расширенное переразрешение истории — отдельная задача.

## 9. Ошибки и частичный импорт

| Случай | Уровень | Результат |
|---|---|---|
| Повреждённый XLSX, неверный лист/заголовки, объединения | Файл | Commit запрещён |
| Дубль ключа в clients или client+period в snapshot | Файл | Commit запрещён, показать обе строки |
| period строк вне объявленного scope | Файл | Commit запрещён |
| Неизвестный клиент/период, ошибка числа, пропуск обязательного | Строка | Строка исключена, отчёт |
| Нет ни одной пригодной строки | Файл | Commit запрещён |
| Есть пригодные и отклонённые строки | Частичная загрузка | Только явное подтверждение администратора, complete=false |
| Повтор commit того же preview | Повтор | Вернуть тот же результат, не создавать срезы повторно |

Транзакция охватывает все **принятые** строки. Частичная загрузка — заранее видимый набор принятых/отклонённых строк, а не случайный обрыв записи. Ошибки отчёта должны быть доступны целиком, не только первыми десятью примерами.

## 10. Повторы, исправления и commit

Идентичность загрузки: SHA256 файла + нормализованный контекст (kind, key_mode, дата, scope, coverage, mapping, версия контракта, supersedes_snapshot_id при его наличии). Go вычисляет request_digest; имя файла в идентичность не входит.

Повтор уже подтверждённой загрузки возвращает прежний результат. Если после частичного импорта требуется дополнить данные тем же файлом, это явная исправляющая загрузка с `supersedes_snapshot_id`, новым контекстом и версией среза, а не скрытый повтор.

Предложение v1: для одной даты существует одна активная версия среза. При другой загрузке той же даты без ссылки на исправление — `SNAPSHOT_DATE_EXISTS`. Исправление должно заменить весь прежний файл этой даты и его period_scope; неявное склеивание запрещено. Старый срез и его строки сохраняются. Перевод активной версии выполняется атомарно. Референсы наследованных total сохраняют прежний источник; исправление не переписывает будущую историю автоматически и показывает предупреждение о зависимых значениях.

Перед commit Go повторно валидирует черновик под транзакцией. Если список принятых строк, разрешённые total или справочники изменились, вернуть `PREVIEW_STALE` и новый preview. Клиент подтверждает только тот результат, который видел. В транзакции блокируются затрагиваемые пары/справочники; простого повторного чтения без защиты от конкурентной записи недостаточно.

## 11. Что требует подтверждения

Техническое решение команды: JSON v1, имена полей, координаты ошибок, разделение Python/Go, явный period, preview/commit, версии исправлений, запрет неявного склеивания, способ вызова парсера.

Поставщик данных: точная принадлежность строк PDF периодам; полный/неполный состав выгрузок; готовность выдавать длинный XLSX с period_code.

Продуктовые правила: значение «реакция», хронический долг, частичное выполнение обещания, поведение при отсутствии в срезе, границы циклов работы, права операторов на переназначение. Эти вопросы не нужно решать в парсере.

## 12. Обязательная структура JSON v1

### 12.1. Context — метаданные загрузки

| Поле | Тип | Правило |
|---|---|---|
| contract_version | string | Ровно `"1.0"` |
| file_kind | string enum | `clients` или `snapshot` |
| key_mode | string enum | `anonymous` или `kcr` |
| mapping_profile | string | Непустой ID профиля, поддержанного сервером |
| snapshot_date | string, date | Обязательно только для snapshot; ISO `YYYY-MM-DD` |
| period_scope | string[] | Для snapshot: непустой список кодов без повторов |
| coverage | string enum | Для snapshot: `unknown` / `full_declared` |
| supersedes_snapshot_id | string, UUID | Только snapshot; явно исправляемый срез, если выполняется исправление |

Все четыре общих поля обязательны. У clients поля snapshot_date, period_scope, coverage и supersedes_snapshot_id запрещены. Дополнительные поля context запрещены. Пользователь и права определяются серверной сессией, не содержимым context.

Пример context среза:

```json
{
  "contract_version": "1.0",
  "file_kind": "snapshot",
  "key_mode": "anonymous",
  "mapping_profile": "canonical_xlsx_v1",
  "snapshot_date": "2026-05-21",
  "period_scope": [
    "2026Q1",
    "Y2025"
  ],
  "coverage": "unknown"
}
```

Пример context справочника клиентов:

```json
{
  "contract_version": "1.0",
  "key_mode": "anonymous",
  "mapping_profile": "canonical_xlsx_v1",
  "file_kind": "clients"
}
```

### 12.2. ParserResult — Python → доменный компонент

Корень содержит **только** обязательные contract_version, file_kind, key_mode, nonempty_row_count, rows, errors. Внутренние client_id, preview_id, дата среза, процент, вычисленный этап работы и результат commit сюда не добавляются. Исходные атрибуты клиента, разрешённые схемой clients, передаются внутри data. Контекст передаётся доменному компоненту отдельно вместе с результатом.

| Поле | Тип / смысл |
|---|---|
| nonempty_row_count | integer ≥ 0: число непустых исходных строк при завершённом разборе |
| rows | Массив `{source, data}` нормализованных строк |
| rows[].source | Только sheet: непустая строка; row: integer ≥ 2, реальная Excel-строка |
| rows[].data | Схема clients или snapshot по file_kind, как в разделе 3 |
| errors | Массив ошибок; пустой массив допустим |

Для snapshot все четыре поля data обязательны; total_docs может быть null. У clients external_id обязателен; необязательные пустые поля опускаются. Значения key_mode и file_kind совпадают с context. Дополнительные поля строк и data не принимаются; новые значения заранее вносятся в общую схему.

| Поле ошибки | Тип / смысл |
|---|---|
| scope | `row` либо `file` |
| code | Стабильный код из заглавных латинских букв, цифр и `_` |
| message | Непустое человекочитаемое объяснение; логика UI опирается на code |
| source | Для row: `{sheet,row,column}`; column — строка либо null. Для file допускается null; при ошибке заголовка возможна row=1 |
| raw_value | Исходный примитив: string / number / boolean / null; объект или массив сюда не передаётся |
| key_hint | При доступном ключе: `{external_id,period_code}`; каждое значение string/null. Для clients period_code=null |

scope, code, message, source и raw_value обязательны. key_hint структурно необязателен, но обязателен по правилу обработки, когда соответствующий ключ удаётся извлечь. Нельзя терять известный ключ только потому, что в другой колонке неверное число.

Каждая непустая строка находится либо в rows, либо среди row-ошибок. Несколько ошибок одной строки считаются одной отклонённой строкой. Для завершённого разбора:

`nonempty_row_count = число rows + число уникальных пар (sheet,row) в row-ошибках`.

При ранней структурной ошибке непрочитанное количество строк не угадывается; file-ошибка блокирует импорт независимо от счётчиков. Сбой программы не является корректным ParserResult.

Пример: две пригодные строки одного клиента по двум периодам и одна ошибочная строка:

```json
{
  "contract_version": "1.0",
  "file_kind": "snapshot",
  "key_mode": "anonymous",
  "nonempty_row_count": 3,
  "rows": [
    {
      "source": {
        "sheet": "snapshot",
        "row": 2
      },
      "data": {
        "external_id": "AAA00001",
        "period_code": "2026Q1",
        "total_docs": 100,
        "unsent_docs": 40
      }
    },
    {
      "source": {
        "sheet": "snapshot",
        "row": 3
      },
      "data": {
        "external_id": "AAA00001",
        "period_code": "Y2025",
        "total_docs": 80,
        "unsent_docs": 0
      }
    }
  ],
  "errors": [
    {
      "scope": "row",
      "code": "INVALID_INTEGER",
      "message": "unsent_docs must be an integer",
      "source": {
        "sheet": "snapshot",
        "row": 4,
        "column": "unsent_docs"
      },
      "raw_value": "12,5",
      "key_hint": {
        "external_id": "AAA00002",
        "period_code": "2026Q1"
      }
    }
  ]
}
```

### 12.3. Preview — доменный компонент → UI

Этот DTO описывает уже доменную проверку, поэтому counts учитывают и ошибки парсера, и отклонение по справочникам/истории.

| Поле | Тип / смысл |
|---|---|
| contract_version | string `"1.0"` |
| preview_id | UUID черновика; не является разрешением доступа |
| status | Для доступного к просмотру результата — `preview_ready` |
| preview_hash | Строка SHA256 результата preview; подтверждается именно эта версия |
| can_commit | boolean; false при file-ошибке или отсутствии пригодных строк |
| requires_partial_confirmation | boolean; true при отклонённых строках и возможности принять остальные |
| counts | `{input, accepted, rejected}` — числа физических исходных строк, не число сообщений об ошибках |
| complete | boolean; false при пропущенных ошибочных строках. true не доказывает полноту исходной базы поставщика |
| report_path | Путь к полному отчёту ошибок, проверяемому сервером по правам |
| errors | Ошибки того же формата source/code; полный отчёт не ограничивается коротким списком UI |

Для доступного preview `input = accepted + rejected`; до commit бизнес-данные не меняются. UUID и hash не заменяют авторизацию. При file-отказе UI получает явный отказ; при недоступном парсере — техническую ошибку, а не успешный импорт нуля строк. Точные DTO отказов закрепляются в T-08/T-26 до подключения UI.

```json
{
  "contract_version": "1.0",
  "preview_id": "19be1c48-86db-47ca-aed1-f9fb8d4c579c",
  "status": "preview_ready",
  "preview_hash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "can_commit": true,
  "requires_partial_confirmation": true,
  "counts": {
    "input": 3,
    "accepted": 2,
    "rejected": 1
  },
  "complete": false,
  "report_path": "/v1/imports/19be1c48-86db-47ca-aed1-f9fb8d4c579c/errors",
  "errors": [
    {
      "scope": "row",
      "code": "INVALID_INTEGER",
      "message": "unsent_docs must be an integer",
      "source": {
        "sheet": "snapshot",
        "row": 4,
        "column": "unsent_docs"
      },
      "raw_value": "12,5",
      "key_hint": {
        "external_id": "AAA00002",
        "period_code": "2026Q1"
      }
    }
  ]
}
```

Запрос commit:

```json
{
  "preview_hash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "accept_partial": true
}
```

При наличии отклонённых строк нужно accept_partial=true. При изменении preview согласие сбрасывается. Успешный ответ содержит contract_version, import_id, counts, complete, already_committed и для snapshot — snapshot_id. Повтор возвращает тот же импорт/срез без второй записи; already_committed=true сообщает о повторе.

### 12.4. Чтение для ML

Кандидаты операций: find_clients, count_clients, get_client_summary, get_client_history. Точные DTO tools — отдельное расширение-предложение T-26/ML; схема ParserResult из-за него не меняется.

Обязательные свойства будущего чтения: серверная проверка доступа, реально применённые фильтры, явный period_code, дата наблюдения, источник числа, различие пустого результата и ошибки. Список и счётчик применяют одинаковые ограничения; количество считается по оговорённой сущности — уникальные клиенты или наблюдения client + period. Это нельзя менять между вопросами молча.

Модель не получает произвольный SQL и не вызывает запись, commit, назначение или смену этапа. Идентичность пользователя берётся из серверной сессии. Источники и scope заполняет сервер. При отсутствии или несвежести наблюдения модель сообщает ограничение, не подставляет ноль.

## 13. Общая модель хранения

Это логическая схема v1. Наличие таблицы в описании не означает, что миграция применена.

| Таблица | Содержимое / ключевой инвариант |
|---|---|
| app_users | Пользователь и роль |
| clients | Внутренний UUID, уникальный строковый external_id, атрибуты клиента; без одного «текущего долга» на все периоды |
| periods | Код, подпись и включительные даты; пересечение периодов допустимо |
| import_batches | Контекст, автор, digest, preview/commit и итог импорта |
| import_rows | Черновые строки, source и ошибки; staging не виден как принятые данные |
| snapshots | Дата наблюдения, версия, связь исправления; одна активная версия даты |
| snapshot_periods | Заявленный period_scope среза |
| snapshot_values | Значения client + period в snapshot; уникальность этой тройки, 0 ≤ unsent ≤ total, источник наследованного total |
| client_period_work | Этап и включение в работу для пары клиент + период |
| assignments | Один активный оператор клиента с историей переназначений |
| events | Общая история клиента; occurred_at отличается от recorded_at |
| event_periods | Какие периоды затрагивает событие; обещание хранится по соответствующему периоду |

Начальный импорт использует справочники и таблицы import/snapshot; полный рабочий процесс не блокирует parser. ИНН не уникален, назначение оператора — на клиента, этап/обещание — по периодам. Отдельные cycle и признак хронического долга не вводятся до продуктового определения. Произвольное удаление истории не является способом исправить импорт.
