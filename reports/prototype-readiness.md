# Проверка готовности прототипа

Дата: 23.11.2026. Версия паспорта: 3. Исходная версия main: `ca2ac88` (PR #105).

Проверены опубликованные исходники, Compose, обработчики Go, Python-парсер, адаптер интерфейса, контракт API, отчёты и паспорт. Техническая проверка не является приёмкой заказчиком или ревью другим участником команды.

## Найдено и исправлено

| Расхождение | Исправление |
|---|---|
| В ownership.md вызов парсера значился будущей задачей #58 | Указан работающий HTTP-вызов, разделены контрольный probe и настоящий импорт |
| Не было актуальной схемы компонентов | Добавлена [схема](../docs/architecture/components.md), сверенная с Compose, прокси, Go и импортом |
| OpenAPI обещал /auth/login и /slices/{id}/errors | Удалены отсутствующие маршруты. Указаны демонстрационная идентификация и формирование CSV в браузере |
| В контракте отсутствовали preview и accept_partial | Описаны предпросмотр 200 без записи, подтверждение 201, согласие на частичный импорт и ошибки |
| Лимит страницы по умолчанию не совпадал с Go | Исправлен на 200, максимум 1000 |
| Даты выходных моделей Go описывались как date | Указан date-time для time.Time в ответах; входные даты остаются YYYY-MM-DD |
| В отчётах сохранились утверждения о неслитой ветке и отсутствии любых замеров людьми | Разделены выполненная техническая проверка и предварительная сессия одного человека |

## Что проверено

- Все 18 пар метод/маршрут в OpenAPI сопоставлены с регистрацией обработчиков; все внутренние ссылки `$ref` разрешаются.
- Добавлен `TestOpenAPIRoutesMatchHandlers`: он сравнивает контракт с AST регистрации Go и выявляет как несуществующие маршруты, так и недокументированные обработчики.
- Повторно пройдены 25 тестов Python-парсера, HTTP, схемы и качества данных; 26 тестов интерфейса и правил; 10 тестов оценщика и состава runtime; 8 тестов сценариев развёртывания. Ошибок нет.
- Проверены отсутствие записи в preview, повторная проверка в транзакции, явное согласие на частичный импорт, ограничение загрузки и удаление временных файлов.
- Просмотрены проверки операторских действий в Go и store: администратор готовит пул, операторы сами распределяют клиентов. Передача и освобождение не выдаются за звонок.
- Веточная проверка CI перед публикацией обязательна: Go с PostgreSQL, Compose smoke, отказ/восстановление Python, реальный XLSX через Go/Python/БД, безопасность и три Docker-образа. Результат хранится в проверках соответствующего коммита GitHub.

В текущем локальном окружении нет Docker, PostgreSQL и компилятора Go. Поэтому локальные unit-тесты не выдаются за новый локальный сквозной запуск. Отдельный чистый запуск и интеграционные проверки выполняет GitHub CI. Базовый main уже прошёл [полный CI #34](https://github.com/KoznovaAV/Re-Hub/actions/runs/45075861219); новый регрессионный тест проверяется в CI изменения.

## Технический чек-лист

Схема, описание интеграции и структуры данных, негативные сценарии, ограничения и запуск имеют свидетельства. Процесс ветка -> PR -> CI -> просмотр diff -> слияние описан в [CONTRIBUTING](../CONTRIBUTING.md) и применяется в репозитории. Согласование этих правил всеми участниками и отдельное одобрение другим человеком не заявляются.

Пункт о бэклоге означает, что задачи, приоритеты и остаточные оценки обновлены. Оценки являются предложением для команды, а не подтверждёнными трудозатратами. Проверка доступного времени остаётся открытой: часы команды не предоставлены.

## Что нельзя закрыть техническим прогоном

1. H-00: один участник, Excel B 36,076 с и Re:Hub B 7,329 с, правильные списки. Разные границы таймера и повторные попытки ограничивают вывод. Нужны два независимых администратора и согласованный эталон. [Отчёт](h00/single-participant.md).
2. H-06: технические проверки карточки не заменяют сессию с операторами. Нужны реальные участники и результаты заданий.
3. Причина 243 неизвестных ID: технический P-04 завершён, но деловое объяснение зависит от поставщика. Доля 5,78% превышает порог 5%.
4. Промышленная аутентификация и управление сотрудниками отсутствуют. Клиентские X-Role и X-User-Id позволяют подменить демонстрационную личность; проверка ролей не устраняет это ограничение.
5. Требуется подтверждение заказчиком окончательных правил статусов и видимости данных. Автоматические проверки показывают соответствие реализованным правилам, но не заменяют согласование.

## Повторение

Команды запуска и проверок находятся в [README](../README.md). Для проверки схемы открыть [components.md](../docs/architecture/components.md). Для независимой проверки API запустить `go test -run TestOpenAPIRoutesMatchHandlers ./internal/api` из backend. Для тестов с БД задать отдельную `TEST_DATABASE_URL`; эксплуатационную БД использовать нельзя.
